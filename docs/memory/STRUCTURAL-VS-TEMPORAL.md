# Pattern: Structural vs Temporal Memory

A complement to the L0-L3 memory model. Both axes apply: every piece of context falls somewhere on L0-L3 **and** is either structural or temporal.

## Statement

Split an agentic system's memory into two categories based on **how often it changes**:

- **Structural**: changes rarely (weeks, months). Always relevant. Guides navigation and decisions. → **Always loaded** (e.g. `AGENTS.md` or `CLAUDE.md` at the project root, auto-loaded by the tool).
- **Temporal**: changes every session, sometimes several times. Snapshot with a timestamp. → **Loaded at boot only** (e.g. `CONTEXT.md` regenerated by `boot.sh`).

Never mix the two in the same artifact: it's an anti-pattern that forces either reloading the structure at every boot (wasteful) or booting just to access the structure (latency + temporal dependency on something stable).

## Classification criteria

| Question | Answer → category |
|---|---|
| "Does this info change multiple times per week?" | Yes → **temporal** · No → **structural** |
| "Does this info stay true regardless of the current session?" | Yes → **structural** · No → **temporal** |
| "Does interpreting this info require a timestamp?" | Yes → **temporal** · No → **structural** |
| "Does this info guide navigation or architectural choices?" | Yes → **structural** · No → **temporal** |

Typical cases:

| Info type | Category | Where |
|---|---|---|
| Project identity, owner | structural | `AGENTS.md` (or tool-equivalent) |
| Directory architecture, streams | structural | `AGENTS.md` |
| Script and config paths | structural | `AGENTS.md` |
| Memory table (what loads when) | structural | `AGENTS.md` |
| Project rules (commit style, granularity, audit) | structural | `AGENTS.md` |
| Current session objective | temporal | `STATE.md` |
| Open loops, session decisions | temporal | `STATE.md` |
| TODO now/next/blocked | temporal | `TODO.md` |
| Pipeline counts, file ages | temporal | `CONTEXT.md` (generated) |
| Git status, recent commits | temporal | `CONTEXT.md` (generated) |

## Grey zones

Some info is **semi-structural**: its *shape* is stable but its *content* evolves.

| Info | Tension | Convention |
|---|---|---|
| List of active handoffs (names) | Workstream structure stable · state volatile | Names + categories → structural; statuses + ages → temporal |
| Active machine in multi-machine setups | Infra structural · current session temporal | Machine list → structural; session's machine → temporal (STATE.md) |
| Available skills | Stable but depends on installed plugins | Auto-injected by the tool harness; don't duplicate |
| Staleness thresholds | Structural but referenced in temporal warnings | Config file referenced from both sides |

General rule: **names/structure** → structural layer; **state/dates/counts** → temporal layer.

## Benefits

1. **Always-on map**: structure is available from the first message of a session, no boot required. Questions like "where does a new script go?" answered immediately.
2. **Focused boot**: `CONTEXT.md` only contains what actually changed. Re-booting truly refreshes rather than re-loading unchanged structure.
3. **Single source of truth**: structure lives in one place (tracked in git). No drift between two parallel files.
4. **Token efficiency**: structure auto-loaded once (prompt cache hit), temporal reloaded only when needed.

## Cost

- Editorial discipline: at write time, decide whether a piece of info is structural or temporal. Common mistake: adding to STATE.md something that belongs in `AGENTS.md` (e.g. "available machines: foo, bar").
- Requires a mechanism for auto-loading the structural layer. In Claude Code: `CLAUDE.md` at the root, auto-read by the harness. In Codex/Cursor: their respective conventions (`AGENTS.md`, `.cursorrules`). Without this mechanism, the pattern has nothing to leverage.

## Anti-patterns

### AP1 — Re-inject the structural into the temporal

`generate_context.py` copies the project-identity file into `CONTEXT.md` on every boot.

**Symptom**: rebooting produces a file identical to the previous one (except for the timestamp). The boot is mostly pointless.

**Fix**: remove the structural layer from the temporal generator, trust the auto-loading mechanism.

### AP2 — Store temporal in the structural

Putting "objective of the week" in `AGENTS.md`.

**Symptom**: `AGENTS.md` changes every couple of days, becomes noisy in git log, loses its function as a stable map.

**Fix**: move back to `STATE.md`, keep `AGENTS.md` at the right change frequency (weeks/months).

### AP3 — Duplicate structural × N

Having `SEED.md` + `AGENTS.md` + a `README.md` that all describe the same architecture.

**Symptom**: every structural change requires updating 3 places. Guaranteed drift.

**Fix**: 1 source of truth (`AGENTS.md`), others point to it.
